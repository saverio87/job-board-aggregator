Recon field notes · job board aggregation

Where the Data Lives

How I worked out, site by site, whether each job board serves its data as an API, hides it inside the page, or hands it over as plain HTML — and why "does it have an API?" was the wrong question to start with.

Section 01

The wrong question

I started out asking each site does it have an API? That question is a trap. It is a yes/no that hides everything useful, and both answers mislead.

A site can have no API and still hand you clean structured data. teast.co has no API at all and turned out to be the easiest of the five to read. A site can also have a perfectly good API that returns almost nothing: eslcafe.com offers a real JSON endpoint whose list response carries five fields and no job description.

The question that actually pays is this: where does the data live, and how many steps does it take to get it? Everything in this document comes out of that one.

Section 02

Four ways data reaches a page

When you ask a server for a web page, the data you want gets to your screen in one of four ways. Almost every site you meet uses one of these, and identifying which one is the whole job.

The one people miss

Row three is where most people — including me, in this very investigation — get it wrong. You fetch a page, search the visible HTML for job titles, find none, and conclude "the data is loaded by JavaScript, I'll need a browser."

Then you look a little harder and find 182 jobs sitting right there in the page, as JSON inside a script tag. No browser needed. Nothing was ever hidden; I was just looking in the wrong part of the file. That is exactly what happened on jobs.echinacities.com.

The habit that fixes this

When the visible markup has no content, don't reach for a browser. Reach for a text search across the whole file for a field name you'd expect in the data — company_name, salary, jobTitle. If it appears, the data is embedded and you can have it in one request.

It's per page, not per site

One more thing worth internalising: a single site can use different patterns on different pages. It is never "this site is an API site." timeshighereducation.com serves its job list as an embedded JSON blob but its job detail pages as fully server-rendered HTML. You ask the question per page, not per domain.

Section 03

How to tell which one you're looking at

There's no cleverness to this. It is a short, boring, repeatable sequence — and the boring part is the point, because it works the same way on a site you've never seen.

  1. Ask for the page, and read the headers before the HTML

    Headers are small, honest, and often name the platform outright. Reading them first saves you from reading 200,000 characters of markup to learn something that was in the first five lines of the response.

    curl -sS -D - -o /dev/null https://example.com/

  2. Check robots.txt and the sitemap

    Two things at once: whether you're welcome, and sometimes a full inventory. echinacareers.com has neither a robots file nor a sitemap — itself a useful signal about how well maintained it is. eslcafe.com, by contrast, allows crawling and publishes a working sitemap.

  3. Count the yield before anything else

    Do this early, because it can end the investigation. If a board carries none of the jobs you care about, it does not matter how clean its API is. eslcafe.com has the cleanest API of the five and carried exactly one relevant job out of 304 — which told me not to lean on it.

  4. Look for the data in three places, in this order

    First the visible markup. Second the script tags and any JavaScript variables — this is the embedded-JSON case, and it's the one skipped by reflex. Third, only if the first two come up empty, the linked JavaScript files, looking for a URL that a request gets sent to.

  5. Probe every URL you find, and read what comes back

    Status code, content-type, and the actual shape of the body. This is where you find out whether the thing you found is a real data endpoint or just more presentation.

    curl -sS -D - -o body.txt 'https://example.com/api/list?page=1'

  6. Work out the parameters by reading the markup, not by guessing names

    This one cost me real time. On jobs.echinacities.com I guessed four plausible page-parameter names in a row; all four returned identical data with no error, which looks exactly like "this site doesn't paginate." The right answer was in the href of the pagination links, where I should have looked first.

  7. Write down the traps while they're fresh

    Every site has at least one behaviour that will silently corrupt a scheduled job. They are invisible later and expensive to rediscover, so record them the moment you find them.

Section 05

Five sites, five answers

The same method, run five times, landing on four different patterns. Note how little of each answer was clever — most of it was reading a header and then looking in the right place.

eslcafe.com

API call
Header said
x-aspnetmvc-version: 5.2, x-powered-by: ASP.NET — Microsoft, server-side.
So I looked at
What scripts the page loads. It pulled in angular.min.js and a file called app.js.
Found
Inside the page's own controller: var searchApiUrl = 'api/list/PostAJobList', called with $http.get. The site tells you its own endpoint if you read its JavaScript.
Calling it gave
application/json, with a tidy envelope containing a paging block and a data array. A genuine API — the only one of the five.

echinacareers.com

HTML fragments
Header said
server: Microsoft-IIS/10.0 with ASP.NET MVC 5. No React, no Angular — old-fashioned server rendering.
So I looked at
The page's script list, then the one custom file in it: jobSearchJS.js.
Found
$.ajax({ url: "/Jobs/JobSearchAJAX" }), and the callback named the variable partialViewResult. The word partial is the tell.
Calling it gave
text/html — a few dozen <div>s, not JSON. Not an API. The browser receives a prepared chunk of page and drops it straight into the document.

timeshighereducation.com/unijobs

Server-rendered + embedded
Header said
x-madgex-proxy. Not a bespoke build — a job-board platform, which matters because anything I learn here likely transfers.
So I looked at
The page for an RSS link, on the hunch that a job board would publish one.
Found
Two things. A feed at /unijobs/jobsrss/ with real publication dates, and — better — a ClientGoogleTagManagerDataLayer object buried in the page containing the job's title, salary, posting date, employer and a full subject taxonomy as structured JSON.
Worth knowing
The structured data was sitting inside an analytics tracking block. Those blocks exist to feed Google, and they're the last place people think to look for data.

teast.co

Embedded JSON
Header said
x-powered-by: Next.js, server: Vercel. Modern React, which meant I had a strong prior before reading a single tag.
So I looked at
Straight for __NEXT_DATA__, the script tag Next.js uses to hand the page its data.
Found
Everything. The complete job list, each entry with roughly fifty fields — including the full job description, a structured subject tag list, and timestamps. All of it delivered with the page. No second request needed.
The catch
Knowing the platform told me where to look in about ten seconds. This is why reading headers first pays.

jobs.echinacities.com

Embedded JSON
Header said
Set-Cookie: PHPSESSID, served by OpenResty. PHP, likely templated server-side.
So I looked at
The visible markup for job listings. Found none, and concluded the page loads its results with JavaScript.
Wrong. Then found
After searching the whole file rather than the markup: var _searchJobList = {"num":182, "list":[…]}. All 182 results, embedded, one request, no browser required.
The lesson
I made the mistake this document warns about, in the middle of writing this document. "Not in the visible HTML" is not the same as "not in the response."
Section 06

What fooled me

These are the failures, because they generalize better than the successes do. Each one is a way a site tells you something untrue without ever returning an error.

Trap 1 — the page number that lies

teast.co took ?p=2, parsed it correctly into its own query object, and returned page one anyway. jobs.echinacities.com ignored four different page parameters in a row and returned the same 25 jobs every time, while still reporting a total of 182.

A page parameter that silently returns page one is the most dangerous failure we hit, because it looks like it works. You'd page through, get repeated results, and conclude the site was smaller than it claimed — capturing six of thirty-two jobs forever, with nothing in any log to suggest otherwise.

The guard: assert that each page's item IDs differ from the previous page's, and compare how many you collected against the total the source itself reports. That second check is free — the number is already in the payload.

Trap 2 — the search that isn't a filter

The keyword search on jobs.echinacities.com returned 182 results for "Computer science." Filtering them properly left 13 that were actually computer-science teaching jobs — about seven percent precision.

A source's own search is a candidate generator, never a filter. Ask it for anything vaguely related, then do the real filtering yourself against fields you control.

Trap 3 — the silent zero

On eslcafe.com, omit the jobType parameter and you get HTTP 200, a valid response envelope, and zero rows. No error, no warning. Omit sortColumn instead and you get a 500 with a full stack trace.

The zero is the dangerous one, because a scheduled job receiving zero results looks identical to a day with no new postings. Never treat an empty result as "nothing new" without a second signal that the request was well-formed.

Trap 4 — the parameter named for the opposite of what it does

jobs.echinacities.com paginates with per_page. It looks like a page size. It is actually an offset — per_page=50 means "skip the first fifty," not "fifty per page." The same page also has a genuine 25/50 results-per-page selector, so the name is doubly misleading.

The general rule: when a parameter appears to do nothing, read the pagination links' href values. The site will tell you its own parameter names if you stop guessing and start reading.

Trap 5 — no date where you need one

echinacareers.com's list data contains no date at all. The only posting date lives on each job's individual detail page, one request per job, rendered as relative prose: "Posted 22 days ago."

So on echinacareers, filtering to "the last month" costs about a thousand requests, while taking everything costs a hundred. Filtering made it ten times more expensive.

And a relative date can't be reconstructed later — it's relative to when you fetched it. Record the date on the run where you first see a job, or lose it permanently.

Section 07

The checklist

Everything above, compressed to something you can run against a new site without re-reading the rest.

  • Fetch the page. Read headers first. Write down the platform.
  • Check robots.txt and the sitemap.
  • Count the yield — does this site even have your jobs? Stop here if it doesn't.
  • Search the whole file for an expected field name before looking for endpoints.
  • Visible markup → script tags and JS variables → linked JavaScript files. In that order.
  • Probe every URL you find. Note status, content-type, and body shape.
  • Never guess parameter names. Read the hrefs and the JavaScript.
  • Check whether the list data carries a date. If not, plan to record first-seen yourself.
  • Page through and confirm each page differs from the last.
  • Compare collected count against the source's own reported total.
  • Write the traps down immediately.
Section 08

Plain-English glossary

The vocabulary I used without explaining, now explained.

API
A URL that answers with data rather than a web page. You ask for a thing and get back a description of it, ready for a program to read.
endpoint
One specific URL on a server that does one specific job. A site has many.
JSON
A way of writing structured data as plain text — labelled fields and values, in a format both humans and machines can read. The thing you want instead of HTML.
header
Small pieces of information the server sends alongside every response, before the actual content. Content type, server software, cookies. They're the fastest way to identify what you're dealing with.
content-type
The header that says what kind of thing is being sent. application/json means data; text/html means a web page. Half the identification work is reading this one line.
server-rendered
The server assembles the complete page, content included, before sending it. What arrives is what you see.
AJAX
A page fetching extra information from the server after it has loaded, without reloading. It's how a page updates a list without flickering.
hydration / embedded data
The server sends a page that already contains the data as a hidden JSON block, so the page's JavaScript can read it without a second request. Fast, and easy to miss when you're only reading the visible markup.
curl
A command-line tool for fetching a URL and showing exactly what came back — no browser, no rendering, no interpretation. Tells you what the server actually said.
partial / fragment
A chunk of HTML that isn't a complete page, sent so the browser can slot it into an existing one.
CORS
A rule browsers follow, not a lock on the server. Normally a web page at one site may not read data from another. A server that wants to allow it sends a permission header. If it doesn't, browsers refuse to hand the data to the page's JavaScript — but the server has already sent it, and any tool that isn't a browser ignores the rule entirely. It protects users from being silently spied on; it does not restrict you.
minified
Code with all its spacing, comments, and meaningful names stripped out to make the file smaller. Still readable by machine, still full of the URLs you're looking for — just unpleasant to read.
